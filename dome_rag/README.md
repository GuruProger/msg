# DomeKB — база знаний агента «Купол выживальщика»

DomeKB — локальная база знаний для ИИ-агента станции «Купол». Она отвечает на
вопросы по корпусу документов, но главное — **не даёт агенту выдумывать**:
каждый ответ собирается из подтверждённых фактов, гипотез, известных пробелов и
цитат. Если данных нет, база честно отказывается отвечать.

Проект работает на чистой стандартной библиотеке Python: без `pip install`, без
numpy, без YAML и без обязательных сетевых моделей.

---

## 1. Три слоя, которые нельзя смешивать

| Слой | Что хранит | Где | Когда используется |
|---|---|---|---|
| **Текст** | документы, регламенты, FAQ, журналы | `chunks/`, `build/vectors.json`, SQLite FTS5 | вопрос «что написано / почему / как» |
| **Факты** | узлы, параметры, команды, пороги, интерлоки, политики, пробелы | `data/`, `data/curated/`, SQLite-таблицы | точные значения и правила |
| **Живые данные** | телеметрия, состояния, ответы API | только WebSocket в момент запроса | вопрос «что сейчас» |

Живая телеметрия **никогда не индексируется** и не попадает в базу. Иначе
ответ «сейчас 725 ppm» устарел бы через минуту и стал бы ложью. Для живых
значений есть команда `py kb.py live snapshot` и клиент `builder/live.py`.

## 3. Команды

| Команда | Назначение |
|---|---|
| `py kb.py build` | всё сразу: извлечение, нарезка, векторы, SQLite, отчёт |
| `py kb.py ingest` | извлечь узлы, параметры, команды, отказы, FAQ из корпуса |
| `py kb.py chunk` | нарезать документы и журналы на чанки |
| `py kb.py vectors` | пересчитать TF-IDF векторы |

| `py kb.py ask "<вопрос>"` | ответ-конверт: факты, гипотезы, пробелы, действия, цитаты |
| `py kb.py ask "<вопрос>" --json` | тот же ответ в машинном виде (для агента) |
| `py kb.py ask "<вопрос>" --llm` | пересказ через DeepSeek (нужен `DEEPSEEK_API_KEY`) |
| `py kb.py stats` | размеры таблиц и распределение чанков |
| `py kb.py eval` | hit@1, hit@5, MRR, answer_ok, abstention |

| `py kb.py live snapshot` | снимок телеметрии через WebSocket |
| `py kb.py live describe` | каталог узлов и разрешённых действий |
| `py kb.py live query --node … --query …` | запрос данных узла |
| `py kb.py live control --node … --command … --value …` | команда (осторожно) |
| `py kb.py live say --text "…"` | сообщение Оператору через `meeting_01` |

Полезные фильтры поиска:

## 4. Структура проекта

```text
dome_kb/
├── kb.py                  # CLI
├── builder/
│   ├── paths.py           # все пути проекта
│   ├── md.py              # парсинг markdown (заголовки, таблицы, списки)
│   ├── ingest.py          # корпус → узлы/параметры/команды/отказы/FAQ
│   ├── chunker.py         # документы → чанки с метаданными и провенансом
│   ├── episodes.py        # журналы смен → эпизоды истории
│   ├── vectors.py         # TF-IDF (слова + символьные 4-граммы)
│   ├── db.py              # схема SQLite и сборка
│   ├── retrieval.py       # гибридный поиск и структурные выборки
│   ├── answer.py          # маршрутизация, конверт ответа, уверенность
│   ├── evaluator.py       # метрики на eval/questions.json
│   ├── report.py          # отчёт о расхождениях
│   └── live.py            # WebSocket-клиент живого API (stdlib)
├── data/                  # сгенерированные структуры (не править руками)
├── data/curated/          # ручные факты: пороги, интерлоки, политики, пробелы
├── chunks/                # сгенерированные чанки (JSONL)
├── build/
│   ├── kb.sqlite          # полнотекстовый и структурный индекс
│   ├── vectors.json       # разреженные векторы
│   └── reports/drift.md   # отчёт о расхождениях
└── eval/questions.json    # 42 размеченных вопроса
```

**Правило владения.** `data/curated/` и `eval/` поддерживаются руками и
версионируются. `data/*.json`, `chunks/`, `build/` генерируются и никогда не
правятся вручную: следующая сборка их перезапишет.

## 5. Почему гибридный поиск, а не только эмбеддинги

В предметной области много точных идентификаторов: `IL_CO2`, `E07`,
`bed_clear`, `probe_z`, `TH_RESUME_LIMIT`, `F-6.6`. Плотные эмбеддинги часто
«размывают» такие строки, а ошибка в одном символе меняет смысл.

Поэтому поиск совмещает:

1. **FTS5 BM25** — точные слова и префиксы;
2. **разреженный TF-IDF** — слова + символьные 4-граммы (устойчивость к русской
   морфологии: «температура / температуры / температурный»);
3. **бусты** — редкий идентификатор, дата, сущность узла, совпадение заголовка;
4. **штрафы** — отрицания («не работает» не должно подтверждаться фразой
   «принтер работает»), примеры кода и дубли.

Векторы лежат в `build/vectors.json` и допускают замену на плотные: достаточно
положить список чисел вместо `{term: weight}`. Встроенная точка расширения —
`sentence-transformers`:

```powershell
$env:DOMEKB_EMBEDDINGS = "st"
$env:DOMEKB_ST_MODEL = "intfloat/multilingual-e5-small"
py kb.py vectors
```

Без установленного пакета база молча останется на TF-IDF — сборка не упадёт.

## 6. Формат ответа

Любой ответ — это конверт, а не только текст:

```json
{
  "question": "…",
  "intent": "DIAGNOSTIC",
  "abstained": false,
  "facts": ["…подтверждено…"],
  "hypotheses": ["…возможно, не доказано…"],
  "unknown": ["…чего не хватает…"],
  "actions": ["…что делать…"],
  "citations": [{"kind": "chunk", "source": "…", "title": "…"}],
  "confidence": {"score": 0.68, "level": "medium", "reason": "…"},
  "chunks": ["…"],
  "mode": "deterministic"
}
```

`facts` — то, на что можно опираться. `hypotheses` — каталог отказов и мнения
жильцов. `unknown` — пробелы, из-за которых нельзя отвечать уверенно.
`abstained` — база сознательно отказалась отвечать.

По умолчанию режим детерминированный: одинаковый вопрос даёт одинаковый ответ.
`--llm` добавляет пересказ, но факты, цитаты и уверенность всё равно считаются
локально.

## 7. Провенанс и статусы

У каждого чанка есть `source` (документ и раздел), `verification_status` и
флаг `has_gaps`.

| Статус | Смысл |
|---|---|
| `normative` | правило, регламент, API-описание |
| `catalog` | описание **возможного** отказа, а не факт станции |
| `observed` | подтверждено записью истории |
| `logbook_opinion` | мнение жильца из бортового журнала, не факт |
| `hypothesis` | значение требует проверки |

Записи с `[ЗАПОЛНИТЬ]` получают `has_gaps=true` и **не могут быть единственной
опорой ответа**. Отчёт `drift.md` показывает такие документы и их количество.

Отдельно различаются:

* **каталог отказов** — «так может быть» (`09_faults.md`);
* **история** — «так было» (`12_history.md`, `Logs/`);
* **мнение** — «жилец считает, что было так» (`logbook.jsonl`).

Утверждать «этот отказ происходил» можно только по `observed`/журналу.

## 8. Живой API

Протокол — WebSocket + JSON, порт по умолчанию `8765`. Штатный пример в
`01_API.md` требует `websockets`, поэтому в `builder/live.py` реализован
минимальный клиент на `socket`: рукопожатие, маскирование кадров, ping/pong,
текстовые фрагменты.

```powershell
$env:DOME_HOST = "192.168.8.10"
$env:DOME_KEY  = "<ключ команды>"

py kb.py live snapshot
py kb.py live snapshot --node printer_3d_01
py kb.py live describe
py kb.py live query --node printer_3d_01 --query list_files
py kb.py live say --text "Нужна проверка стола принтера"
```

Если адрес или ключ не заданы, команда завершается с понятным сообщением и
кодом `2`. Сетевые ошибки обрабатываются так же — без трассировки стека.

**Важно:** `success: true` означает, что сервер **принял** команду, а не что
устройство её выполнило. После команды нужно проверить результат по
телеметрии (`verify_by`). Физические действия выполняет только Оператор.

## 9. Оценка качества

Набор `eval/questions.json` содержит 42 вопроса: 38 с ожидаемым ответом и 4
проверки отказа (пароль Wi-Fi, серийный номер, состав экипажа, погода на Марсе).

Текущие метрики (`py kb.py eval`):

| Метрика | Значение |
|---|---|
| hit@1 | **0.711** |
| hit@5 | **0.921** |
| MRR | **0.799** |
| answer_ok | **1.000** |
| abstention | **1.000** |

`hit@k` считает попадание ожидаемого фрагмента в текстовый топ. Часть вопросов
(`q04` — 75 °C, `q08` — 90 %, `q20` — GAP-001) отвечается из структурных таблиц
SQLite, поэтому у них `rank=None` при корректном `answer_ok`. Это ожидаемое
поведение, а не промах поиска.

## 10. Ограничения и известные пробелы

* **Нет нейросетевых эмбеддингов по умолчанию.** TF-IDF силён на точных
  терминах, но слабее на сложных перефразах. Точка замены предусмотрена.
* **GAP-001 не закрыт.** Два документа по-разному распределяют 8 линий щита;
  `knowledge/03_energy.md` §5.6 прямо говорит, что подтверждённой таблицы нет.
  База не утверждает, какая линия питает конкретное устройство. Ориентир —
  `lines[].name` в живой телеметрии и сообщение Оператора.
* **5 чанков с `has_gaps`.** Это документы с `[ЗАПОЛНИТЬ]`; они помечаются в
  ответе и не считаются полным источником.
* **Часть порогов — гипотезы.** В `thresholds.json` есть значения со статусом
  не `confirmed`; в ответе они помечаются явно.
* **Не все узлы есть в реестре.** Для дополнительных датчиков название и
  система восстановлены по телеметрии; это отмечено в `drift.md`.
* **У части измерений нет единиц.** Отчёт перечисляет такие параметры.
* **Живые данные не кэшируются.** История телеметрии доступна только через
  журналы `Logs/`, а не через базу.
* **Один эпизод истории.** В корпусе только смена `2026-10-14`; остальные
  журналы отсутствуют.

## 11. Что проверяет `drift.md`

Отчёт генерируется автоматически и содержит:

1. сводку (узлы, параметры, команды, чанки, пробелы);
2. таблицу конфликта назначения линий щита с отметками реальных расхождений;
3. документы с `[ЗАПОЛНИТЬ]` и число чанков с `has_gaps`;
4. распределение чанков по типам и статусам проверки;
5. узлы без команд, измерения без единиц, узлы без названия;
6. дубли и почти-дубли;
7. открытые пробелы с ответственным;
8. источники и контрольные суммы SHA-256.

Это не украшение, а защита от галлюцинаций: отчёт показывает, где документы
противоречат друг другу и что нельзя считать подтверждённым.
