# Поддержка документации и декларации

## 1. Область обновления

Документация охватывает `dome_agent`, `dome_control`, `dome_dashboard`,
`dome_web`, `dome_rag` и связанный зачетный порядок эксплуатации. Источники
фактического поведения - текущий код и результаты проверки; источники
обязательных требований - переданный PDF, обязательные разъяснения
организаторов и согласованная декларация. Тексты корпуса RAG не заменяют
регламент. Недостаток реализации отмечается отдельно, а не скрывается
утверждением о полном соответствии.

## 2. Карта изменений

| Изменение | Документы и свидетельства |
|---|---|
| Версия, входы/выходы, данные, автономность, модель | README, декларация, матрица, PROJECT_SNAPSHOT |
| Цикл, control, policy, verify, rules, state | ARCHITECTURE, REFERENCE, INCIDENTS, журнал решений |
| Логи, seq/ref, формат evidence | REFERENCE, DECISION_LOG, матрица пп. 10.2-10.3 |
| RAG: корпус, источники, coverage, LIVE | ARCHITECTURE, REFERENCE, OPERATIONS, corpus manifest, декларация |
| Фронт, чат, настройки модели | OPERATIONS, REFERENCE, декларация (включая модель чата) |
| Новый официальный регламент/разъяснение | Исходный документ, матрица, декларация, процедуры кризисов |
| Тесты и проверка на площадке | README/REFERENCE с датой, средой и фактическими результатами |

## 3. Порядок обновления

1. Скопировать прежние документы и хеши в резервную папку. Не архивировать
   ключи и `.env`. Установить, какое рабочее дерево документируется.
2. Прочитать измененные пути исполнения и тесты; не ограничиваться заголовком
   патча. Проверить реальные имена команд, полей и endpoint-ов.
3. Для каждой затронутой нормы отметить: реализовано, организационный шаг,
   частично или не подтверждено. Фраза «описано в инструкции» не означает
   наличие программной блокировки.
4. Обновить технические разделы и декларацию. Если меняются данные,
   интерфейсы, версия или автономность, повторно зафиксировать их до старта
   по п. 5.3; порядок допуска согласовать с организаторами.
5. Для кода выполнить подходящие локальные проверки. Для правок только
   Markdown проверить ссылки, команды, таблицы, отсутствие старых
   противоречащих утверждений и секретов; новый прогон оборудования не нужен.
6. Зафиксировать SHA-256 исходников, политики, manifest и исходного PDF.
   Обновить дату и PROJECT_SNAPSHOT.json. Не присваивать новый Git-коммит
   незакоммиченному рабочему дереву.
7. Сохранить исходные журналы без редактирования. Дополнения и исправления
   оформлять отдельной записью со ссылкой на оригинал.

## 4. Неизменные требования зачетного профиля

* Приоритет безопасности, отсутствие вмешательства в аппаратные блокировки.
* Только подтвержденная DeepSeek V4 Flash во всех AI-вызовах финальной игры.
* Явные данные/интерфейсы, исполнитель, полномочия, проверка результата и резерв.
* Для normal/auto не считать success API доказательством физического эффекта.
* Не повторять неясную команду после потери связи/рестарта.
* Для false alarm требуются независимые данные, их время и зона; RAG не дает
  права отменить аппаратную защиту.
* После аварийной остановки действует п. 9.4, а не только исчезновение hold.
* В заявленном профиле исключены yolo и force; текущая реализация технически
  допускает их выбор, что должно быть явно отражено в ограничениях.
* Полный аудит хранится отдельно от ограниченной сводки и памяти чата панели.

## 5. Контроль перед передачей

- Ссылки относительные; все названные файлы существуют.
- Подтвержденные факты отделены от рекомендаций и еще не выполненных условий.
- Перечислены реальные доступные инструменты, включая read-only knowledge.
- Нет прежних утверждений «RAG вне runtime», старого console script панели
  и нерелевантного числа тестов.
- Декларация содержит ответственных или явно незаполненные организационные поля.
- API-идентификатор разрешенной модели не выдуман.
- Веса критериев оценки и скрытые сценарии кризисов не придуманы: пп. 7.4, 11.3.
- Не заявлено, что локальные тесты подтверждают допуск настоящего оборудования.
